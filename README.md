# Тендерный помощник ИП

B2B веб-инструмент для агрегации, парсинга и анализа тендерных данных (goszakup + Самрук-Казына) за прошлые годы с использованием RAG-поиска и ИИ-ассистента.

## Технологический стек

- **Backend:** Node.js 22.22.3 + TypeScript + NestJS
- **Frontend:** React 19 + Next.js 16
- **Package manager:** pnpm 12
- **Дальнейшие этапы:** PostgreSQL/pgvector, объектное хранилище и фоновые задачи будут добавлены отдельными задачами.

## Структура репозитория

```text
tender-assistant/
  backend/          # Серверная часть (NestJS API)
  frontend/         # Клиентская часть (Next.js)
  infra/            # Инфраструктурные скрипты и конфигурации
  docs/             # Документация и спецификации
```

## Local development

### Требования

- Node.js `22.22.3`. Версия зафиксирована в `.nvmrc` и используется в точном Docker image `node:22.22.3-bookworm-slim`. Оба варианта удовлетворяют требованиям Vitest 5/Vite 8 (`>=22.12.0 <23`).

  ```bash
  nvm install
  nvm use
  ```

  Если `nvm` не используется, установите Node.js `22.22.3` другим способом.
- pnpm `12.4.1`. Если pnpm не установлен глобально, включите Corepack:

  ```bash
  corepack enable
  corepack prepare pnpm@12.4.1 --activate
  ```

- Docker Engine с Docker Compose v2 — только для контейнерного сценария. Docker Engine в текущей песочнице недоступен, поэтому image build и Compose нужно проверить в CI или на машине с Docker.

### Запуск приложений напрямую

1. Установите зависимости из корня репозитория:

   ```bash
   pnpm install
   ```

2. Создайте локальные файлы конфигурации:

   ```bash
   cp backend/.env.example backend/.env
   cp frontend/.env.example frontend/.env.local
   ```

   `BACKEND_INTERNAL_URL` используется только server-side Route Handler Next.js. Браузер всегда обращается к same-origin endpoint `/api/v1/health`; внутренний URL backend не попадает в клиентский JavaScript.

3. Запустите backend и frontend одновременно:

   ```bash
   pnpm dev
   ```

4. Откройте <http://localhost:3001>. Страница должна показать `Сервер доступен`.

   Проверить backend напрямую можно так:

   ```bash
   curl --fail -i http://localhost:3000/api/v1/health
   ```

   Проверить frontend Route Handler и его proxy к backend можно так:

   ```bash
   curl --fail -i http://localhost:3001/api/v1/health
   ```

   Ожидаемый успешный ответ содержит поля `status`, `service` и `timestamp`, например:

   ```json
   {
     "status": "ok",
     "service": "tender-assistant-backend",
     "timestamp": "2026-01-01T00:00:00.000Z"
   }
   ```

### Запуск через Docker Compose

Docker Compose не требует локальных `.env`-файлов: безопасные development-значения заданы в compose-файле.

```bash
docker compose up --build
```

После успешного запуска:

- frontend: <http://localhost:3001>
- backend health: <http://localhost:3000/api/v1/health>
- frontend health proxy: <http://localhost:3001/api/v1/health>

Остановить контейнеры:

```bash
docker compose down
```

Hot reload настроен только для запуска напрямую через `pnpm dev`. Docker Compose собирает production-like образы без bind mounts; после изменения исходников повторите `docker compose up --build`.

### Проверки

Из корня можно выполнить основные проверки:

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
```

Для конфигурации CORS используйте точный production allowlist, например:


Не используйте wildcard `*` для production.

## Проверки в CI

Воспроизводимые GitHub Actions quality gates определены в [`.github/workflows/ci.yml`](.github/workflows/ci.yml) (workflow `CI`).

- **Триггеры:** `pull_request` в `main`, `push` в `main` и вручную через `workflow_dispatch`.
- **Job `quality`** на GitHub-hosted Ubuntu runner: воспроизводимая установка зависимостей `pnpm install --frozen-lockfile` (Node.js читается из `.nvmrc`, pnpm — из `packageManager` в `package.json`, с кэшированием зависимостей через `actions/setup-node`), затем строго по порядку `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e` и `pnpm build`. Ошибка любой команды падает весь workflow.
- **Job `docker-smoke`** запускается после `quality` на GitHub-hosted Ubuntu runner: проверяет `docker compose config`, собирает и запускает контейнеры через `docker compose up --build -d`, bounded retry loop'ом (до 60 секунд на сервис) дожидается readiness и проверяет backend `http://localhost:3000/api/v1/health` и frontend Route Handler/proxy `http://localhost:3001/api/v1/health`, включая валидацию JSON-тела (`status`, `service`, ISO-8601 `timestamp`) без внешних зависимостей вроде `jq`.
- При ошибке запуска или healthcheck workflow печатает `docker compose ps` и последние 200 строк логов обоих контейнеров.
- Cleanup `docker compose down -v --remove-orphans` выполняется отдельным шагом всегда (`if: always()`), независимо от успеха или падения smoke-test.
- В CI нет secrets, deployment-шагов и публикации Docker images; workflow работает без secrets и с read-only правами (`permissions: contents: read`), устаревшие запуски одной ветки/PR отменяются через `concurrency` + `cancel-in-progress: true`.

Тот же набор проверок можно выполнить локально из корня репозитория:

```bash
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
docker compose config
docker compose up --build -d
curl --fail http://localhost:3000/api/v1/health
curl --fail http://localhost:3001/api/v1/health
docker compose down -v --remove-orphans
```

> **Windows PowerShell.** В Windows PowerShell `curl` может быть alias для `Invoke-WebRequest`.
> Для bash-совместимых аргументов используйте `curl.exe --fail ...`,
> либо используйте `Invoke-RestMethod`.

## Конфигурация

- `backend/.env.example` — `NODE_ENV`, порт API и явно заданный список CORS origins.
- `TENDER_LOT_SOURCE` — источник данных публичных страниц лотов: `fixture` (значение по умолчанию,
  в том числе когда переменная не задана) или `goszakup`. Любое другое значение останавливает
  backend с ошибкой `TENDER_LOT_SOURCE must be one of: fixture | goszakup`. Источник выбирает
  только backend: параметром запроса браузер его не переключает.
- `backend/.env.example` также содержит переменные Goszakup: `GOSZAKUP_TOKEN` (пустой по
  умолчанию; обязателен только для `TENDER_LOT_SOURCE=goszakup`), `GOSZAKUP_GRAPHQL_URL`
  (по умолчанию официальный `https://ows.goszakup.gov.kz/v3/graphql`) и `GOSZAKUP_TIMEOUT_MS`
  (по умолчанию 15000). Локальный запуск без секретов всегда fixture-backed.
- `frontend/.env.example` — `BACKEND_INTERNAL_URL`, доступный только server-side Route Handler.
- Реальные `.env` и `.env.local` не должны коммититься. Реальный `GOSZAKUP_TOKEN` нельзя
  коммитить, печатать в логах или передавать во frontend.

```bash
docker compose build
docker compose up -d
curl --fail http://localhost:3000/api/v1/health
```

## CP-03: список → фильтры → карточка

Откройте `/lots` (ссылка также доступна на главной). Next.js server pages обращаются
к NestJS через `BACKEND_INTERNAL_URL`; браузер отправляет GET-форму на тот же origin.
Фильтры сохраняются в URL, ссылкой на результат можно поделиться. Список по умолчанию
показывает все примеры, включая нецелевые; профиль участия указан над фильтрами.

API:

- `GET /api/v1/lots` — массив лотов в стабильном порядке.
- `GET /api/v1/lots/:id` — те же поля одного лота; неизвестный ID возвращает 404.
- `maxAmount` — включительная верхняя граница в KZT, неотрицательное десятичное
  число (до двух знаков после точки); некорректное значение возвращает 400.
- `region`, `district` — точное совпадение без учёта регистра и крайних пробелов.
- `q` — подстрока в названии, заказчике или описании, без учёта регистра.
- Фильтры объединяются через AND. Пустые значения игнорируются; повторение
  поддерживаемого параметра возвращает 400. Неизвестные параметры игнорируются.

Пример: `/api/v1/lots?maxAmount=500000&region=Алматы&district=Алатауский&q=столы`.

Контракт лота: `id`, `source`, `sourceUrl`, `title`, `customer`, `amount` (KZT),
`region`, `district` (строка или null), `bidDeadline` (ISO-8601), `description`,
а с CP-07 — производное `assessment` (см. раздел CP-07), с CP-08 — вложенный
`procurement` (см. раздел CP-08), с CP-09 — производное `timing` (см. раздел CP-09), с CP-10 — `actionability: { status: 'TAKE' | 'REVIEW' | 'SKIP' }`, с CP-11 — вложенное detail-only поле `documents: Array<{ id, name, type, mimeType, sizeBytes, sourceUrl }>`, а с CP-12 — detail-only поле `requirements: { status, items, warnings }`.

CP-10 объединяет только assessment и timing: EXCLUDE → SKIP; иначе CLOSED_BY_DEADLINE → SKIP; иначе REVIEW → REVIEW; иначе DEADLINE_UNKNOWN → REVIEW; MATCH + OPEN_BY_DEADLINE → TAKE; неизвестная комбинация → REVIEW. Список принимает локальный фильтр `actionStatus=TAKE|REVIEW|SKIP`, который никогда не передаётся Goszakup. Это внутренняя операторская рекомендация по настроенным правилам, не официальный статус закупки и не юридическое заключение; причины assessment и данные о сроке остаются источниками объяснения.
Срок в карточке показывается по времени Алматы (UTC+5).

Детерминированные записи находятся только в backend
(`backend/src/modules/tender/lots.fixtures.ts`) и проходят через `TenderService` и API.
Это **вымышленные тестовые данные**, а не действующие закупки. Ссылки ведут в реестр
Goszakup, не на выдуманные объявления. Предусмотрены ЛДСП, металлические шкафы,
сумма ровно 500 000 и выше неё, Алматы/Алатауский район, другой город, а с CP-07 —
неоднозначный пример без товарных признаков для статуса `REVIEW`.
Поиск — буквальный, не классификатор материалов (например, «не ЛДСП» тоже содержит «ЛДСП»).

Регрессии: Jest/Supertest проверяют list/detail, границы суммы, поиск, географию,
комбинации фильтров, ошибки и 404. Vitest с React SSR проверяет запросы страниц к API,
форму, ссылки, поля карточки, пустые результаты и недоступность backend.
Новых runtime/test-зависимостей, хранилищ и deployment-изменений нет.

## CP-04: Goszakup OWS v3 как backend-only источник

`/lots` и `/lots/[id]` по умолчанию работают на детерминированных фикстурах: подключение живого
источника к публичному API определяется конфигурацией backend (CP-05), а отдельного режима
`source=goszakup` не существует. CP-04 добавляет только границу интеграции — чтение официального
реестра и нормализацию в существующий контракт лота.

- Контракт источника: официальный GraphQL OWS v3 — `POST https://ows.goszakup.gov.kz/v3/graphql`,
  схема `https://ows.goszakup.gov.kz/help/v3/schema/`, авторизация `Authorization: Bearer <token>`.
- Один ограниченный read-only путь: `Query.Lots(filter, limit)` (`limit` 1–200; probe берёт 5,
  живой список CP-05 — 20). Мутаций в схеме не используется, повторы запросов не добавлены.
- `GoszakupClient` (`backend/src/modules/tender/goszakup/goszakup.client.ts`) использует
  встроенный `fetch` Node 22 с `AbortSignal.timeout`, различает сетевую ошибку, таймаут,
  HTTP ≠ 2xx (401 — ответ реестра без валидного токена), ошибку GraphQL при HTTP 200 и
  некорректное тело. Текст ошибки дополнительно очищается от токена.
- Нормализация (`goszakup.mapper.ts`) сохраняет: стабильный `id` (`goszakup:<id>`),
  `source = goszakup`, ссылку на карточку реестра, наименование (ru, иначе kk), сумму,
  заказчика и его БИН, срок подачи заявок из `TrdBuy.endDate`, регион по кодам КАТО
  (`plnPointKatoList`) и описание. Поля, которых реестр не отдаёт, остаются пустыми, а не
  выдумываются: `district` всегда `null`, `bidDeadline` пустой без `endDate`. Записи без `id`
  или `amount` отбрасываются.
- Токен живёт только в окружении backend (`GOSZAKUP_TOKEN`); во frontend и в ответах API его
  нет, что проверяется e2e-тестом.
- Живая проверка — отдельная developer-only команда, она ничего не сохраняет и не печатает токен:

  ```bash
  GOSZAKUP_TOKEN=<ваш токен OWS> pnpm --filter @tender-assistant/backend probe:goszakup
  ```

  Без `GOSZAKUP_TOKEN` команда завершается с кодом 2 и сообщением `NOT RUN`; это не ошибка.
  Дополнительно можно задать `GOSZAKUP_GRAPHQL_URL` и `GOSZAKUP_TIMEOUT_MS`.

Все автоматические тесты (client, mapper, source, probe, e2e) работают без токена и без сети:
ответы реестра представлены синтетическими фикстурами в `backend/test/fixtures/`.
Персистентности, очередей, скрейпинга и новых зависимостей CP-04 не добавляет.

## CP-05: контролируемый живой пользовательский путь (Goszakup)

Уже готовая граница CP-04 подключена к публичному пути `/lots` → `/lots/[id]`, при этом
fixture-режим остался режимом по умолчанию, а страницы явно показывают источник данных.

| `TENDER_LOT_SOURCE` | `/lots` и `/lots/[id]` | Токен |
| --- | --- | --- |
| не задан или `fixture` | детерминированные фикстуры CP-03, поведение не изменилось | не нужен |
| `goszakup` | read-only выборка из официального реестра OWS v3 | обязателен `GOSZAKUP_TOKEN` |
| другое значение | backend не стартует: ошибка конфигурации | — |

- **Список.** Один ограниченный запрос `Query.Lots(filter, limit: 20)`
  (`DEFAULT_LIVE_LOTS_LIMIT`): ни исторического обхода, ни пагинации, ни скрейпинга. Счётчик
  в UI честно называет результат ограниченной выборкой, а не полным списком подходящих закупок.
  Фильтры передаются источнику; их безопасное upstream-подмножество строится отдельно, после
  нормализации один общий локальный шаг проверяет все публичные предикаты.
- **Карточка.** `GET /api/v1/lots/goszakup:<id>` — документированный ограниченный lookup
  `Query.Lots(filter: { id: [<id>] }, limit: 1)` по полю `id: [Int]` из `LotsFiltersInput`
  (<https://ows.goszakup.gov.kz/help/v3/schema/lotsfiltersinput.doc.html>). Карточка не зависит
  от того, попал ли лот в первую страницу списка. Лоты других id-префиксов, некорректный id или
  id вне диапазона GraphQL `Int` получают 404 без обращения к реестру; отсутствующая в реестре
  запись — тоже 404; сбой реестра — 503.
- **Статус источника.** `GET /api/v1/lots/source` возвращает
  `{"mode":"fixture","live":false,"label":"Demo fixtures"}` или
  `{"mode":"goszakup","live":true,"label":"Goszakup"}`. В ответе нет токена, его наличия,
  адресов реестра и других внутренних настроек.
- **Индикатор доверия.** `/lots` и `/lots/[id]` показывают `DEMO · Demo fixtures · синтетические
  данные` или `LIVE · Goszakup · данные получены онлайн (только чтение)`. Карточка дополнительно
  показывает `lot.source` и ссылку на реестр.
- **Отказы.** Если в live-режиме реестр недоступен, отвечает неавторизованно или `GOSZAKUP_TOKEN`
  не задан, backend возвращает безопасный 503 `Lot source is temporarily unavailable` (без токена,
  адресов и стектрейсов), а страницы показывают сообщение о временной недоступности и **не**
  подставляют демо-примеры под видом живых данных. Фикстурный режим от доступности Goszakup не
  зависит.

Проверка живого режима на своей машине (токен не коммитится и не печатается):

```bash
TENDER_LOT_SOURCE=goszakup GOSZAKUP_TOKEN=<ваш токен OWS> \
  pnpm --filter @tender-assistant/backend dev
curl --fail 'http://localhost:3000/api/v1/lots/source'
curl --fail 'http://localhost:3000/api/v1/lots'
curl --fail 'http://localhost:3000/api/v1/lots/goszakup:<id из выдачи>'
```

Детерминированные тесты (Jest/Supertest и Vitest) работают без сети и без токена: выбор источника
по умолчанию, явные `fixture` и `goszakup`, некорректное значение `TENDER_LOT_SOURCE`, живой список
и живая карточка через подменённый транспорт реестра, некорректные id, отсутствующая запись, сбой
реестра без утечки токена, `/api/v1/lots/source`, а также индикаторы источника, состояния
«недоступно» и отсутствие подмены фикстурами в UI.

## CP-06: целевой ограниченный live-поиск

Фильтры списка теперь доходят до `LotSource`; Goszakup source строит upstream-фильтр через чистый
переводчик, а `TenderService` после нормализации единожды применяет полный публичный набор условий.
Для официального `LotsFiltersInput` подтверждены поле `nameDescriptionRu` и смысл поиска по
русскому наименованию/описанию с морфологией ([официальная схема](https://ows.goszakup.gov.kz/help/v3/schema/lotsfiltersinput.doc.html)); только публичный
`q` передаётся в это поле. API-клиент делает ровно один bounded GraphQL-запрос на список.

`maxAmount` остаётся локальным: документация описывает `amount: [Float]` как поиск по сумме лота,
но не устанавливает семантику диапазона/верхней границы. `region` также остаётся локальным:
`plnPointKatoList: String` не документирует формат безопасного поиска по префиксу КАТО; район
не представлен в фильтрах лота. Коды и диапазоны не угадываются. Поэтому `/lots?maxAmount=500000&region=Алматы&deadlineStatus=OPEN_BY_DEADLINE`
— открытая ссылка пресета «Наш профиль» (CP-09 добавляет к ней локальный фильтр по сроку),
которая заполняет форму и не добавляет непроверенный текстовый запрос.

Ограничение: Goszakup текстовый фильтр ограничен русским названием/описанием и использует морфологию;
он не заменяет локальную подстрочную проверку и не гарантирует полный охват (LIVE-выборка по-прежнему
ограничена одной страницей). Район Алатау — только локальное предпочтение, если upstream данных
района нет. Все CP-06 проверки используют фикстуры и fake transport; реальный targeted live probe
не выполняется без настроенного токена.

## CP-07: детерминированный предварительный отбор (MATCH / REVIEW / EXCLUDE)

Каждый публичный ответ лота содержит производное поле `assessment`:

```json
{
  "status": "MATCH",
  "reasons": ["Amount is within 500,000 KZT", "Region is Almaty", "LDSP signal found"]
}
```

Поле считается на backend одной чистой функцией
(`backend/src/modules/tender/lot-assessment.ts`) из уже нормализованного лота, поэтому
фикстуры и живые записи Goszakup идут одним путём: list и detail дают одинаковый результат,
входной лот не мутируется, сеть не используется, новых зависимостей нет, сырые DTO реестра
в assessment не попадают.

| Статус | Когда выставляется |
| --- | --- |
| `EXCLUDE` | сумма > 500 000 KZT, либо регион известен и не Алматы, либо в названии/описании есть явный признак металлического шкафа |
| `MATCH` | жёсткие исключения не сработали, сумма ≤ 500 000 KZT, регион — Алматы и есть положительный товарный признак (ЛДСП/LDSP или мебель) |
| `REVIEW` | всё остальное: лот не исключён, но данных для автоматического решения не хватает |

Правила намеренно узкие и консервативные:

- металлический шкаф — только «металлический(-ие) … шкаф(-ы)» рядом, в любом порядке; слово
  «металл» само по себе, металлическая дверь, стеллаж или стол ничего не исключают;
- мебель — короткий фиксированный список (мебель, шкаф, тумба, кухня, стол в обычных формах);
- отсутствующий регион или район никогда не исключает лот, а неизвестный регион не считается
  Алматы; нераспознанный код КАТО — неоднозначные данные, а не «вне Алматы»;
- Алатауский район — только положительная причина (`Preferred district: Alatau`), а не условие;
- причины — короткие стабильные англоязычные строки в фиксированном порядке: сумма, регион,
  материалы, район, затем `Insufficient evidence for automatic match` для `REVIEW`. Regex,
  внутренние коды и сырые значения КАТО в причины не попадают.

Список: `GET /api/v1/lots?status=MATCH|REVIEW|EXCLUDE` (регистр не важен, неизвестное значение —
400). Фильтр применяется локально после оценки и никогда не уходит в Goszakup: семантика
upstream-фильтров CP-06 не менялась, новых запросов в реестр нет.

UI: на `/lots` карточка показывает компактный статус, форма GET получила выбор статуса
(все / MATCH / REVIEW / EXCLUDE), исключённые лоты по умолчанию не скрываются. На `/lots/[id]`
видны причины. Подпись у списка: «Статус — автоматический предварительный отбор по простым
правилам. Финальное решение принимает оператор.»

Это не AI-рекомендация и не скоринг: нет LLM, эмбеддингов, ранжирования, оценки маржи,
юридических выводов, персистентности и новых инфраструктурных изменений.

Проверки: unit-тесты чистого оценщика (границы суммы, регионы, металлические шкафы, ЛДСП,
порядок причин, смешанный регистр, отсутствие мутации входа), e2e fixture-режима (assessment
в list/detail, фильтр статуса, 400 на неизвестный статус), e2e живого режима на подменённом
транспорте реестра (тот же оценщик, статус не уходит upstream), Vitest SSR (бейджи в списке,
причины в карточке, сохранение остальных параметров ссылки). Все тесты — offline и без токена.

## CP-08: данные закупки для решения оператора

Контракт лота дополнен вложенным объектом (только добавление, существующие поля и их
семантика не изменились):

```json
"procurement": {
  "lotNumber": "1",
  "announcementNumber": "0001-1",
  "customerBin": "000740000001",
  "publishedAt": "2026-09-20T08:00:00.000Z",
  "procurementMethod": "Запрос котировок",
  "officialStatus": "Приём заявок"
}
```

Каждое значение — подтверждённое поле официальной схемы OWS v3
(<https://ows.goszakup.gov.kz/help/v3/schema/>), ничего не выводится из свободного текста:

| Поле | Источник в официальной схеме |
| --- | --- |
| `lotNumber` | `Lots.lotNumber` — «Номер лота» |
| `announcementNumber` | `Lots.trdBuyNumberAnno`, иначе `TrdBuy.numberAnno` — оба документированы как «Номер объявления» |
| `customerBin` | `Lots.customerBin` / `Subject.bin` — «БИН заказчика» (теперь отдельным полем, а не только строкой в `description`) |
| `publishedAt` | `TrdBuy.publishDate` — «Дата и время публикации» |
| `procurementMethod` | `TrdBuy.RefTradeMethods.nameRu` (иначе `nameKz`) — «Способ закупки» из справочника методов закупок `RefTradeMethods` |
| `officialStatus` | `TrdBuy.RefBuyStatus.nameRu` (иначе `nameKz`) — «Статус объявления» из справочника статусов `RefBuyStatus` |

Срок приёма заявок остаётся существующим `bidDeadline` ← `TrdBuy.endDate` («Дата окончания
приёма заявок»). Правила соответствия:

- отсутствующие значения — всегда `null`, без заглушек и домысливания; нераспознаваемая дата
  остаётся `null`, а не превращается в выдуманный момент времени;
- сырые числовые коды (`refTradeMethodsId`, `refBuyStatusId`, `refLotStatusId`) в публичный
  ответ не попадают: наборы их значений не документированы, поэтому отдаются только
  человекочитаемые названия из официальных справочников;
- все поля едут в том же единственном ограниченном запросе `Query.Lots(filter, limit)` —
  N+1-обогащения и второго запроса на строку списка нет; маппер остаётся чистым и
  детерминированным;
- фикстуры и живые записи используют один и тот же контракт: в фикстурах покрыты три
  состояния — полные метаданные, частично отсутствующие и полностью отсутствующие
  (значения синтетические, это по-прежнему вымышленные примеры, а не реальные записи
  реестра);
- дублирование БИН в `description` сохранено: `q` CP-06 продолжает искать по описанию, как
  и раньше, а БИН теперь доступен и как структурное поле.

UI: на `/lots/[id]` добавлен раздел «Данные закупки» (номер лота, номер объявления, БИН
заказчика, публикация, приём заявок до, способ закупки, официальный статус); отсутствующие
поля показываются как `Не указано` (срок — принятое ранее «Срок не указан»). Оценка CP-07 и
причины остаются над метаданными, ссылка на источник и индикатор LIVE/DEMO сохранены. Список
`/lots` не разрастается: новые поля на карточки списка не дублируются.

Семантика CP-07 (`assessment`), фильтры и upstream-подмножество CP-06, выбор источника,
обработка ошибок, 404 и LIVE/DEMO-индикатор не менялись. CP-08 — только метаданные и
отображение: это предварительная детерминированная информация из реестра, а не гарантия;
финальная проверка тендера — по ссылке на источник.

Проверки: unit-тесты маппера (номер лота/объявления, БИН, публикация, способ, статус,
отсутствующие и нераспознаваемые значения), e2e fixture-режима (контракт `procurement` в
list/detail, паритет фикстур), e2e живого режима на подменённом транспорте (метаданные в
одном bounded-запросе, минимальная запись без опциональных полей), Vitest SSR (раздел
«Данные закупки» с полными данными и с `Не указано`). Все тесты — offline и без токена.

## CP-09: рабочее окно тендера по сроку подачи заявок

Каждый публичный ответ лота дополнился производным объектом (только добавление, существующие
поля и их семантика не изменились):

```json
"timing": {
  "status": "OPEN_BY_DEADLINE",
  "deadline": "2026-10-15T12:00:00.000Z",
  "remainingMinutes": 20880
}
```

| Статус | Когда выставляется | `remainingMinutes` |
| --- | --- | --- |
| `OPEN_BY_DEADLINE` | корректный срок подачи заявок ещё не наступил (`deadline > now`) | целое неотрицательное число минут, округлённое **вверх** |
| `CLOSED_BY_DEADLINE` | срок уже прошёл или равен текущему моменту (`deadline <= now`) | `null` |
| `DEADLINE_UNKNOWN` | срок отсутствует или не разбирается как дата | `null` |

Правила:

- `timing` считается **только** из нормализованного `bidDeadline` (`TrdBuy.endDate`), одной чистой
  функцией `backend/src/modules/tender/lot-timing.ts` с явно переданным `now`: фикстуры и живые
  записи Goszakup идут одним путём, список и карточка дают одинаковый результат, входной лот не
  мутируется, сеть не используется, новых зависимостей нет;
- текущее серверное время передаётся на границе сервиса, а тесты всегда используют фиксированный
  момент, поэтому результат не зависит от реальной даты запуска;
- округление вверх единственное и задокументировано: срок, который ещё не истёк, никогда не
  показывается как «осталось 0 минут»;
- `deadline` повторяет корректный нормализованный ISO-срок, иначе `null`; человекочитаемая фраза
  в контракт не добавляется;
- **`OPEN_BY_DEADLINE` — не официальный статус закупки.** Это арифметика по сроку: юридический
  статус остаётся в `procurement.officialStatus` (CP-08), а первоисточником — запись источника.
  Названия намеренно исключают короткое `OPEN`.

Список: `GET /api/v1/lots?deadlineStatus=OPEN_BY_DEADLINE|CLOSED_BY_DEADLINE|DEADLINE_UNKNOWN`
(регистр не важен, неизвестное значение — 400, повтор параметра — 400). Фильтр применяется
локально после расчёта `timing` и никогда не уходит в Goszakup: upstream-подмножество CP-06 не
менялось, новых запросов в реестр нет, остальные фильтры продолжают работать в комбинации.

UI: карточка списка показывает компактное состояние срока (`Срок открыт · 2 дн. 4 ч.`,
`Срок истёк`, `Срок не указан`), форма GET получила выбор срока (все / срок открыт / срок не
указан / срок истёк), ссылка остаётся общей. В разделе «Данные закупки» состояние срока показано
рядом со сроком подачи заявок и с оставшимся временем, а официальный статус — отдельным полем;
подпись явно различает эти два факта. Живого таймера и клиентского интервала нет: значение
рендерится на сервере. Тендеры с истёкшим сроком по умолчанию не скрываются — их отбирает только
явный фильтр. Пресет «Наш профиль» дополнительно запрашивает `deadlineStatus=OPEN_BY_DEADLINE`,
и активный фильтр виден в форме.

Семантика CP-07 (`assessment`) не менялась: истёкший срок не превращает лот в `EXCLUDE`, срок —
отдельное операционное измерение. Метаданные CP-08, выбор источника, обработка ошибок, 404 и
LIVE/DEMO-индикатор не менялись. Планировщиков, уведомлений, персистентности и новых
инфраструктурных изменений CP-09 не добавляет.

Проверки: unit-тесты чистого оценщика (будущий, ровно текущий и прошлый срок, отсутствующий и
неразбираемый срок, границы `remainingMinutes`, использование переданного `now`), e2e
fixture-режима на фиксированных часах (`timing` в list/detail, паритет фикстур, фильтр
`deadlineStatus`, 400 на неизвестное и повторённое значение), e2e живого режима на подменённом
транспорте (тот же оценщик, состояние срока не уходит upstream, запись с истёкшим сроком),
Vitest SSR (все три состояния в списке, различение официального статуса и состояния срока в
карточке, сохранение остальных параметров ссылки). Все тесты — offline и без токена.

## CP-11: официальные документы закупки

Проверенный официальный machine-readable путь в схеме Goszakup OWS v3:
- Официальная схема: `https://ows.goszakup.gov.kz/help/v3/schema/`
- Запрос реестра: `Query.Lots(filter: LotsFiltersInput, limit: Int)`
- Тип `Lots`: поле `Files: [FileLots]` («Документ лота»)
- Тип `TrdBuy`: поле `Files: [FileTrdBuy]` («Документ закупки»)
- Поля объектов `FileLots` и `FileTrdBuy`: `id: Int`, `filePath: String`, `originalName: String`, `nameRu: String`, `nameKz: String`.

Границы и правила интеграции:
- Bounded read-only lookup только для карточки тендера: запрос `GOSZAKUP_LOT_DETAIL_QUERY` выполняется только на detail (`GET /api/v1/lots/:id`) с `limit: 1` и фильтром по ID лота.
- Список лотов (`/lots` и `GET /api/v1/lots`) не запрашивает документы у реестра и не возвращает поле `documents` (0 upstream-запросов документов со стороны списка).
- Контракт документов закупки (detail-only):
  ```ts
  documents: Array<{
    id: string;
    name: string;
    type: string | null;
    mimeType: string | null;
    sizeBytes: number | null;
    sourceUrl: string;
  }>
  ```
- Ссылки ведут исключительно на официальный портал Goszakup (`https://goszakup.gov.kz...`). Относительные пути безопасно резолвятся к официальному хосту, сторонние схемы и внешние домены отклоняются в пользу официальной страницы лота. Токен авторизации (`GOSZAKUP_TOKEN`) остаётся исключительно на сервере и никогда не включается в URL или ответы.
- Известные ограничения официального источника: OWS v3 не предоставляет байтовый размер файла (`sizeBytes` всегда `null`) и не содержит семантического классификатора типов документов (`type` всегда `null`). MIME-тип выводится исключительно из расширения файла; при неизвестном расширении поле остаётся `null`.
- Паритет детерминированных фикстур: фикстуры содержат синтетические примеры со множественными документами (`fixture-1`), документом с частичными метаданными (`fixture-2`) и отсутствием документов (`fixture-3`, `fixture-6`).
- Интерфейс: блок «Документы закупки» на странице `/lots/[id]` показывает наименование, метаданные (MIME) и официальную ссылку на первоисточник. При отсутствии документов отображается состояние «Документы не указаны источником.». Ошибка источника отображается как недоступность сервиса и не подменяется ложным пустым списком.

## CP-12: детерминированное извлечение требований

Результаты bounded format reconnaissance по реальным документам Goszakup (`FileLots` и `FileTrdBuy` из CP-11):
- **Путь получения байтов (`Document retrieval path`)**: на детальной карточке (`GET /api/v1/lots/:id`) сервер выполняет ограниченный read-only `GET` к официальным файловым путям портала (`https://goszakup.gov.kz/files/download_file/...`, `https://v3bl.goszakup.gov.kz/files/download_file/...`, `https://v3bl.goszakup.gov.kz/uploads/...`) с жёстким таймаутом, запретом редиректов (`redirect: 'error'`), лимитом размера в памяти (`5 МБ`) и без сохранения на диск. Токен `GOSZAKUP_TOKEN` никогда не отправляется на файловые хосты портала. Если ссылка ведёт на HTML-страницу реестра или портал ограничивает доступ (`Доступ к документу запрещен`), ошибка не роняет карточку, а отражается в `requirements.warnings`.
- **Подтверждённые текстовые форматы (`Supported formats`)**:
  1. **Text-native PDF (`application/pdf`)** — формируемые порталом технические спецификации и протоколы (`/files/download_file/...`), проверяемые по сигнатуре `%PDF-`, структуре объектов и потокам текста (`BT ... ET`, включая `/FlateDecode` и таблицы символов `/ToUnicode` CMap).
  2. **OpenXML DOCX (`application/vnd.openxmlformats-officedocument.wordprocessingml.document`)** — официальные приложения к конкурсной документации (`/uploads/template/...` и прикреплённые `.docx`), проверяемые по сигнатуре ZIP-контейнера `PK\x03\x04` и наличию `word/document.xml`.
- Формат никогда не считается доказанным только по имени файла или `mimeType`: проверка всегда выполняется по фактическим байтам и внутренней структуре документа. Устаревшие бинарные `.doc`/`.xls`, произвольные архивы без `word/document.xml` и отсканированные PDF без текстового слоя не передаются в OCR и помечаются для ручной проверки.

Публичный контракт (detail-only, отсутствует в списке `GET /api/v1/lots`):
```ts
requirements: {
  status: 'AVAILABLE' | 'PARTIAL' | 'UNAVAILABLE';
  items: Array<{
    category:
      | 'SUBJECT'
      | 'QUANTITY'
      | 'DIMENSIONS'
      | 'MATERIAL'
      | 'DELIVERY'
      | 'QUALIFICATION'
      | 'SUPPORTING_DOCUMENT'
      | 'OTHER';
    text: string;
    sourceDocumentId: string;
    sourceLocator: string | null;
  }>;
  warnings: string[];
}
```

Правила и ограничения:
- Ни одно требование не додумывается: каждый элемент `items` создаётся только из фактического текста документа и обязан ссылаться на `sourceDocumentId` и `sourceLocator` (`Стр. N` для PDF, `Табл. N, стр. M` / `Абз. N` для DOCX).
- Упоминания графических чертежей, схем или неполных внешних приложений попадают в `warnings` (`нужно проверить вручную`), переводя статус в `PARTIAL` (при наличии других извлечённых требований) или `UNAVAILABLE`.
- В системе нет OCR, LLM, embeddings, RAG, векторных или реляционных БД, object storage и фоновой индексации.
- На странице `/lots/[id]` блок «Требования» отображает статус (`AVAILABLE`, `PARTIAL`, `UNAVAILABLE`), сгруппированные по категориям требования с указанием документа-источника и локатора, а также блок «Нужно проверить вручную», явно отделяя извлечённые факты источника от операторской рекомендации.
